  There is NO issues/ directory. A FAILURE RECORD lives at two levels. STEP
  level: tests/<id>/steps/<ordinal>-<id>/failure.yaml, authored by the framework
  (or a triage agent), parsed against failure.schema.json. Required core:
  `step` (MUST equal the folder id and match a result.yaml step —
  l1.failure.unmatched), `status` (the verdict enum; disagreement with the
  matched step is an ADVISORY warning l1.failure.status_disagrees), and
  EVIDENCE-OF-WHAT (error.message, or expected+actual). File references
  (repro.definition/resolved, page_state.dom/a11y/screenshot,
  console_at_failure.ref, network_at_failure.ref, triage.rca.evidence[],
  triage.suggested_fix.patch) resolve relative to the TEST ROOT tests/<id>/ —
  no '..', no leading '/', no scheme (l1.failure.ref_escape) — and MUST exist
  (l1.failure.ref_missing); their bytes are never parsed. URLs are open strings,
  never checked. The optional `triage` block is STRICTLY SHAPED when present:
  status ∈ {untriaged, triaged, in_progress, dismissed}; rca requires
  root_cause, confidence ∈ [0,1]; by requires a date-time `at`;
  verification.status ∈ {not_verified, verified, refuted}. Free-form forensic
  blocks (locator_context, error.type, rca.category, linked_defects, …) stay
  OPEN. RUN level: finalize GENERATES a pack-root failure.yaml index — its first
  generative output beyond derived totals/hashes, amending 0040's "finalize is
  unchanged" — with denormalized rows { test, ordinal, step, status, path,
  triage_status? } sorted by test then ordinal, ALWAYS written (failures: [] on
  a clean run), before the atomic seal. finalize FAILS FAST on a record that
  does not parse or lacks a string status. Validation is STATUS-GATED (0018):
  shape/anchor/reference checks run at any status on whatever exists; at
  finalized the index MUST exist (l1.failure_index.missing) and a failed/broken
  step without a record earns an ADVISORY warning (l1.failure.missing). The
  index must be TRUTHFUL: rows agree with their own path
  (l1.failure_index.invalid), pointers resolve (l1.failure_index.dangling), and
  every record present is indexed (l1.failure_index.incomplete) — all hard
  errors, since the index is machine-generated.

## Reasoning

> **Amendment (optional `title`, 2026-07-07).** A step record MAY carry a
> top-level `title` — a short defect-style *name* for the failure, typically
> the investigation verdict's bug title. It is an **open string, never
> cross-checked** (no new codes, no new required fields), and finalize **lifts
> it verbatim** into the index row when it is a non-empty string — the same
> mirror-never-validate posture as the `triage_status` lift. Rationale: triage
> queues and dashboards need a *label*, not just a status — `rca.root_cause` is
> a sentence, `title` is a name. A record-vs-row title mismatch is impossible
> on a freshly finalized pack, since finalize generates the index.

**Why not `issues/`.** The reserved directory imagined failures as a *sibling
concept* beside steps. But a failure's forensics are *about a step* — the
expected/actual, the page state, the console at the moment step N broke. Giving
the record a home *inside the step's own folder* (next to its screenshot) makes
the anchor structural: the folder name already carries `<ordinal>-<id>`, so a
record cannot exist unanchored, and the existing folder⇄step cross-checks
([0030](0030-step-ordinal-semantics.md)) extend naturally. A separate `issues/`
tree would have needed its own naming convention plus a linking field — two ways
to drift.

**Why an index, and why finalize writes it.** A consumer (dashboard, triage
queue) wants "every failure in this run" without opening N tests × M steps. The
pack-root `failure.yaml` gives that in one read, with rows denormalized just
enough (`test`, `ordinal`, `step`, `status`, lifted `triage_status`) to render a
failure table. It is *generated, never authored*: the framework authors step
records, `finalize` aggregates, `validate` only checks — no component does two
jobs. This is finalize's first generative artifact beyond derived totals/hashes
(amending [0040](0040-l1-profile-evidence-artifacts.md)'s "finalize is
unchanged"), written before the [atomic seal](0042-atomic-seal-in-place.md) so it
rides into the zip. Always writing the index (`failures: []` on a clean run)
keeps its presence unconditional at `finalized` — the `coverage/` posture — so
consumers never branch on absence. finalize fails fast on an unreadable record
(the posture it already takes toward a malformed `result.yaml`): sealing a pack
whose index is knowingly broken helps nobody.

**Why the index checks are hard errors.** Because the index is machine-written,
any inconsistency — a row whose `path` disagrees with its own fields, a pointer
to a missing record, a record absent from the index — means tampering or a stale
index, not authoring style. A freshly finalized pack is always index-consistent;
`l1.failure_index.*` errors surface only on modified packs.

**Why strict where it counts, open elsewhere.** The record core and the `triage`
shape are the parts *other tools* build on (triage queues key on `status` and
`triage.status`; verification pipelines on `verification.status`), so they get
closed enums and required sub-fields — snake_case per [0036](0036-snake-case-keys.md).
Everything a *framework* narrates freely — `locator_context`, `error.type`,
`rca.category`, `linked_defects` — stays open, the
[0009](0009-step-kind-open-string.md)/[0012](0012-typed-free-form-metrics.md)
stance. References follow [0029](0029-definition-path-safety.md), resolved from
one unambiguous base (the test root, regardless of the record sitting one level
deeper) — checked for containment and existence, never parsed.

**Why the advisories are advisories.** A failed step without a record, and a
record whose `status` disagrees with `result.yaml`, are *signals*, not
corruption — not every framework emits structured failure records, and the
verdict of record ([0016](0016-test-status-authored.md)) lives in `result.yaml`.
Both warn without failing the pack, mirroring the screenshot advisory in 0040
and `status.disagrees_with_steps`.

## Consequences

- Two new parsed declarations under `src/schemas/0.1/L1/`:
  `failure.schema.json` (step record) and `failure-index.schema.json` (root
  index) — joining `logs-meta` and `video` in the registry.
- `src/validate/l1.ts` gains `checkFailure` (per test: shape, anchor, status
  advisory, reference containment/existence, missing-record advisory) and
  `checkFailureIndex` (global: presence at finalized, shape, row/path agreement,
  dangling, completeness).
- New diagnostic codes: `l1.failure.{invalid, unmatched, ref_escape,
  ref_missing, status_disagrees (warn), missing (warn, finalized)}` and
  `l1.failure_index.{missing (finalized), invalid, dangling, incomplete}`.
- `finalize` enumerates `steps/*/failure.yaml` per test, lifts rows, writes the
  sorted root index before sealing; throws on an unparseable record.
- The `issues/` line leaves the L1 tree in
  [`design/contract/04-L1.md`](../contract/04-L1.md); a "Failures" section
  documents both levels. 0040 carries an amendment note.
- Conformance corpus: `fixtures/0.1/L1/` gains failure-record fixtures (full
  record + matching index; advisory cases; each error code), and every
  finalized L1 fixture now carries the root index.
- Deferred, additively: parsing referenced artifact bytes, hashing failure
  artifacts at finalize, closed vocabularies for the open forensic fields,
  cross-test failure dedup/ranking.
